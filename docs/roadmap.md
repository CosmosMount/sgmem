## 候选方向的优先级

| 优先级 | 方向 | 实现复杂度 | 现有依据 | 主要限制 |
|---|---|---|---|---|
| 1 | 问题引导的元数据轻量重排 | 低 | 93/179 dev 题存在唯一群组线索；有明确人物/观点混淆案例 | 群组正确仍可能没有关键内容；线索不明确时应保持原检索 |
| 2 | 有界回复扩展后重排，作为第一项的可选补充 | 中低 | 两跳图可达性从 6/28 到 10/28，包含同级回复案例 | 更多候选不等于更好的 top-10；固定挤入两条回复可能牺牲有效原证据 |
| 3 | 在同群组、同话题内处理更新版本 | 中 | 已有漏掉更新、采用旧方案的案例 | 最新不必然正确；部分更新已在 top-10 但 QA 仍未采用 |
| 4 | BM25 与 Dense 的轻量融合，再加入元数据 | 中低 | 全量仅 BM25 正确 112 题、仅 Dense 正确 82 题，存在互补 | 这是描述性观察，不是融合增益；纯融合不足以满足元数据贡献要求，还会增加索引成本 |
| 暂缓 | 大型图系统、训练新模型或扩展新基准 | 高 | 本轮没有证明这些额外开销必要 | 项目重点是可归因的结构信息作用，现有预算优先完成受控实验与分析 |

排序依据是当前数据、实现负担和课程要求，不是已测得的提升排名。[GroupMemBench 论文 §4.3–4.4](https://arxiv.org/html/2605.14498v1#S4.SS4) 也提示复杂记忆处理未必优于保留原消息的检索；其模型配置不同，不能把论文中的瓶颈比例直接移用于本地 Qwen3-8B。

## 首选方案保持多简单

保留现有 BM25/E5 的内容分数和模型，只增加一个轻量重排步骤。

1. 从问题中的明确群组、阶段、话题名称得到线索。对歧义或无匹配的情况，回退原排序；对明确问“我说了什么／我的观点”的问题，才考虑 asker 的身份，不能只要出现 I/my 就过滤。
2. 取基础检索器的一小批候选，加入群组、阶段/话题和适用的人物匹配分数。优先软加分，保留跨群组和跨参与者证据的机会。基础分数的归一化、候选数及少量权重在 dev 上确定，最终仍只提供 10 条不同消息。
3. 先比较有、无这一步的变化；仅当错误证据支持时，再加入受限的回复候选。父消息、子回复和同级回复的范围要明确，候选需去重并按内容相关性选择，不能无条件占满两个回复名额。

在已有 28 条支持证据失败记录中，13 条的原 top-10 已全部属于正确群组。14 条可得到群组线索的记录中，只有 5 条的原候选混有其他群组。真正应验证的是最终检索到的具体证据以及问答结果。

时间处理先作为后续独立消融。对相对日期做确定性解释或改 QA 提示，可能有助于已召回证据却答错的案例，但属于 QA 层变化；若采用，应给所有对照同样的处理并重新比较，不能算作检索结构的单独收益。

## 下一轮的最小验收

- 先与用户确定实现方案、服务器和 GPU 预算。前序临时卡号或共享许可不能视为一直有效。
- 实现只接收公开问题与可见消息，合成例验证歧义回退、目标人物、ID 去重和最终 K。再跑少量真实 dev 题，核对候选、提示、输出与计时。
- 在固定 dev 179 题上比较一个候选方法与已有 BM25、Dense。为区分收益来源，至少给出候选方法去掉元数据后的同预算对照；避免大量权重搜索。
- 选择依据包括总体/六类正确率、成对修复和退化数、代表案例以及延迟/token/GPU-hours。当前 28 条支持记录是事后诊断集，不能代替 dev QA，也不能把目标 ID 输入检索。
- 确定代码与配置后冻结，在 test 536 题上做一次正式比较；保留失败、无提升和退化，不依据 test 反复调整。
- 在最终报告中能回答：哪些错误被改好、哪些新错误被引入、元数据本身贡献了多少、额外成本多少。
