# 实施路线图

| 阶段 | 可并行工作 | 依赖与交付验收 |
| --- | --- | --- |
| 0：项目约定 | 核对课程原文和上游规则；分配角色和资源 | 审阅本设计并建立首次提交；确认可用硬件、预算、协作者及共享位置 |
| 1：共享契约 | 数据字段核验、合成样例、schema、配置和运行记录设计；报告大纲 | 合并 `feat/core-contracts`，定义 ID、查询、结果、可见性和版本约定；CPU 测试可运行 |
| 2：基线闭环 | GroupMemBench adapter、BM25、Dense、QA/evaluator、资源记录各自分支 | 逐步合并；用合成和少量真实样例跑通可重复的小规模流水线，验证无答案/未来信息泄漏与上游评测对齐 |
| 3：错误分析 | 在 dev 上比较基线，建立分类与标注规则；记录资源 | 有逐题记录、覆盖率、错误分母和可核查案例；确定 SGAR 特征是否有依据 |
| 4：方法与评测 | SGAR 与特征消融、效率分析、报告和代码走查 | 开发集选择权重并冻结，运行配对 test；保存 manifest、完整轨迹和实际资源消耗 |
| 5：交付 | 结果复核、报告、海报与个人面试演练 | 每张表可追溯，诚实呈现局限和失败，另一成员可解释核心实现与典型案例 |

集成负责人先合并公共契约，其他成员可依据草案并行准备但需在接口稳定后更新；基线完成和分析之后再冻结 SGAR 实验。EverMemBench 和其他模型作为可选扩展，不能挤占核心评测及可靠性工作。具体负责人与时间由团队根据成员人数和课期在看板上认领，避免预设虚构人选。
