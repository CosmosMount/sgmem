## 本轮完整探索

下表在新一轮模型判分前确定。各方向先检查可实现性、公开触发和候选覆盖，再统一进入开发集比较。实现复用现有数据、BM25、E5、runner 和判分流程，使用固定的小量配置。最终选一个能解释元数据贡献的方案。

| 顺序 | 探索方向 | 最小实现与对照 | 要回答的问题 |
|---|---|---|---|
| 1 | 元数据进入索引 | 对 role、group、phase、topic 构建简短可检索文本，与正文索引比较；speaker 仅按显式目标使用 | 目标消息是否首次进入候选池，元数据词是否挤占正文信号 |
| 2 | 群组与阶段定位 | 处理相同位置嵌套的名称，保留真正并列的范围；在公开范围内用去掉字段名称后的内容词召回，再与全文分支合并 | 能否修复名称歧义及长背景词主导检索的问题 |
| 3 | 目标人物与角色 | 显式人物、完整角色，或与个人状态谓词相连的 I/my 触发；保留内容候选 | 能否减少 speaker、belief 及 group 混淆，同角色的不同人是否仍混在一起 |
| 4 | 条件时间排序 | 在公开人物或范围已经匹配、问题明确询问当前状态时，对同范围候选使用有限的时间次序信号 | 能否找到更新状态，是否误删仍有效的旧证据或反对意见 |
| 5 | BM25 与 Dense 融合 | 固定等权 RRF，分别比较内容融合与加入公开元数据后的融合 | 收益来自两种内容检索互补，还是元数据贡献 |
| 6 | 与有界回复扩展组合 | 对最有依据的内容/元数据候选补充同群回复，比较带回复与去掉回复 | 新候选与回复结构是否互补，是否引入新的上下文干扰 |
| 7 | 问答失败与成本诊断 | 逐题比较支持证据、回答截断、judge 和资源数据；检查已召回支持仍答错的案例 | 检索增益能否转成 QA 增益，瓶颈是否转移到问答阶段 |

RRF 使用文献中的排名融合形式，固定平滑常数 60。每种方法最终提供十条原始消息，内部候选深度和实际使用的列表数量逐项记录。E5 使用现有固定权重、query/passage 前缀和其原有截断方式。[RRF 原论文](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf) · [E5 模型说明](https://huggingface.co/intfloat/e5-small-v2)

## 实验矩阵与执行顺序

第一轮固定比较八个候选配置，分别是字段索引、范围召回、范围加人物、范围加条件时间、内容 RRF、RRF 加元数据、元数据加回复，以及主问句加全文的双分支召回。它们共享实现，配置承担明确的对照或消融作用。若某配置没有实际触发或无法提供合法的十条消息，记录原因并在进入模型运行前修正或淘汰。

1. 在固定 179 道 dev 上完成全部候选的检索检查。检查全部题目的唯一 ID、公开输入、消息预算、触发数量及基线一致性。对已有支持标注分别统计进入候选池、进入前十、增益和损失；标注只在检索完成后参与统计。
2. 每个待运行配置先做小规模真实问答，检查提示、输出和资源。随后对全部 179 道 dev 重新回答并判分。既有 BM25、Dense、回复方法保留为固定对照，核对相同数据、模型修订、提示模板和生成设置。
3. 一次性汇总八个配置的总体、六类、四域、逐题修复/退化以及成本。按 dev QA 正确题数选择，再结合元数据相关修复、额外成本和代码复杂度处理并列。小样本支持命中作为解释证据。
4. 冻结所选方案及对应的去元数据对照后，各运行一次 536 道 test。依据测试结果撰写结论，并保留负结果与失败案例。
5. 按“探索矩阵与 CPU 验证”“完整 dev 比较”“冻结 test 与报告”提交可复现成果；每阶段检查 GitHub 更新和代码一致性。

按此前单个 179 题运行约 0.44 GPU-hours 估算，八组 dev 与两组 test 约需 6.2 GPU-hours，加上预检和索引开销，申请本轮最多 8 GPU-hours。该额度包含 Qwen3-8B、已有 E5 和判分，实际分项记录。服务器启动前需要一张约 20 GiB 以上空余显存的卡；预算和新模型调用由用户一次性确认。2026-11-21 检查时八张卡均未达到这一空余量，CPU 实现与检索诊断可以先推进。

时间处理先作为后续独立消融。对相对日期做确定性解释或改 QA 提示，可能有助于已召回证据却答错的案例，但属于 QA 层变化；若采用，应给所有对照同样的处理并重新比较，不能算作检索结构的单独收益。

## 本轮完整验收

- 先与用户确定实现方案、服务器和 GPU 预算。前序临时卡号或共享许可不能视为一直有效。
- 实现只接收公开问题与可见消息，合成例验证歧义回退、目标人物、ID 去重和最终 K。再跑少量真实 dev 题，核对候选、提示、输出与计时。
- 在固定 dev 179 题上统一比较上述八组配置与已有 BM25、Dense、两种回复方法。为区分收益来源，选定方法需要对应的去元数据对照；避免大量权重搜索。
- 选择依据包括总体/六类正确率、成对修复和退化数、代表案例以及延迟/token/GPU-hours。当前 28 条支持记录是事后诊断集，不能代替 dev QA，也不能把目标 ID 输入检索。
- 确定代码与配置后冻结，在 test 536 题上做一次正式比较；保留失败、无提升和退化，不依据 test 反复调整。
- 在最终报告中能回答：哪些错误被改好、哪些新错误被引入、元数据本身贡献了多少、额外成本多少。
