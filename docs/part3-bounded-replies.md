# Part 3 · 有界回复扩展

`bm25-reply` 在 15 条已标注的 BM25 失败记录中多找回了一条支持消息。在四域 179 道固定开发题上，它与原 BM25 均答对 56 题（31.28%），逐题判定一致。E5 Dense 答对 58 题（32.40%）。[检索记录](evidence/bounded-reply-dev.json) · [问答结果与逐题判定](evidence/bounded-reply-qa-dev.json)

## 固定开发集问答

2026-11-17 在干净的 `4bcf725` 上用 Qwen3-8B 对全部 179 题重新生成回答并判分。BM25 与 E5 Dense 使用 Part 1 已保存的同题结果。数据、模型修订、提示、每次调用的种子、输出预算和严格判分规则均已核对。表中为答对题数。

| 题型 | 题数 | BM25 | BM25 + 回复 | E5 Dense |
|---|---:|---:|---:|---:|
| 多跳推理 | 45 | 13 | 13 | 16 |
| 知识更新 | 27 | 5 | 5 | 5 |
| 时间推理 | 40 | 9 | 9 | 7 |
| 隐含用户信息 | 13 | 8 | 8 | 6 |
| 术语歧义 | 27 | 2 | 2 | 9 |
| 拒答 | 27 | 19 | 19 | 15 |
| **总体** | **179** | **56** | **56** | **58** |

**与 BM25 逐题配对，修复 0 题，退化 0 题。** 165 道题的实际回答提示哈希和最终回答均一致。另 14 道题的提示确实改变，其中 9 道的回答文字改变。原答对的 4 道仍然答对，原答错的 10 道仍然答错。与 Dense 配对，29 道只有回复方法答对，31 道只有 Dense 答对。Part 2 已标注的 BM25 失败中，说话人混淆和群组混淆各有 1 条，两条均未修复。

- **证据已送入模型。** Technology 的 `multi_hop_2` 问过期可用性该用什么规则。新找回的 `Msg_847` 明说用一条回退规则，同一句还提到针对硬性阻断的另一条规则。Qwen 把两者都写进回答，judge 对照只要求前者的参考答案判错。这条消息改变了回答，但没有改变正式得分。
- **证据进入候选池。** Manufacturing 的 `multi_hop_24` 问清理电子表格前该优先用哪个数据源。支持消息 `Msg_29329` 指出先查控制系统趋势，其自身 BM25 分数为 9.17，在新增候选中排第五。两格给了得分 11.56 和 11.27 的消息。Qwen 最终选择了电表导出数据，仍然答错。

正式运行完成 179 次回答、179 次判分，调用错误、无法解析的判分和判分截断均为 0。两条回答达到 512 token 上限，均按实际输出计分。单张 RTX A6000 用时 25 分 49 秒（0.4303 GPU-hours），峰值已分配显存 15.79 GiB。独立的一题预检用时 0.0065 GPU-hours，另计。新方法尚未在 536 道冻结测试题上评估。

## 方法

1. BM25 检索公开的提问者 ID 和问题文本。问题出现建议、提案、讨论、反馈或回复等英语线索时，才启用扩展。完整词表在[检索实现](../src/sgmem/retrieval.py)中。
2. 最终取十条时，固定原前八条，从这八条沿同一群组的父消息或子回复走至多两跳，可找到同一父消息下的另一条回复。每个节点最多看一个父节点和八个子节点。若子回复超过八条，只看按时间排序的最早四条、最晚四条，中间的证据可能因此漏掉。
3. 候选按自身 BM25 分数排序。同分优先原前十中的消息，再优先较短路径和原语料顺序。只有正分且至少达到原第十名分数一半的回复能竞争末尾两个位置。空位由原排序补齐，消息 ID 去重。进模型的仍是十条消息，图中的路径单独留在检索记录里。

每题只做一次内容打分。扩展最多检查 `8 × (9 + 9²) = 720` 次邻接关系，诊断记录最多保留原十条和十条新增候选。标注支持 ID 只参与事后核对。

## 固定开发集的检索结果

改动题数统计 179 题中前十成员与 BM25 不同的题数。其余各列只统计 **15 条有支持消息标注的 BM25 开发集失败记录**。每条命中表示至少一条已标注支持进入相应集合。两项原始基线只有已保存的前十可供比较。

| 方法 | 改动题数 / 179 | 候选池命中 / 15 | 最终前十命中 / 15 | 较 BM25 新增 / 丢失 |
|---|---:|---:|---:|---:|
| 原 BM25 | 0 | 4 | 4 | 0 / 0 |
| 原 E5 Dense | 179 | 5 | 5 | 2 / 1 |
| 一跳、两个位置 | 15 | 4 | 4 | 0 / 0 |
| 两跳、一个位置 | 14 | 6 | 4 | 0 / 0 |
| 两跳、两个位置，对所有问题启用 | 158 | 6 | 4 | 1 / 1 |
| **两跳、两个位置，按问题启用** | **14** | **6** | **5** | **1 / 0** |

- Technology 的 `multi_hop_2` 沿 `Msg_638 → Msg_832 → Msg_847` 找回了支持消息，排在第十位。一跳和只留一格均错过了它。
- Manufacturing 的 `multi_hop_24` 找到了 `Msg_29329`，但它的内容分数不足以进入前十。原 BM25 已找到的四条支持在选定规则下保留了原排名。
- 较早的试验让回复继承部分起点分数，改变了 88 道题的前十，最终只命中 3/15。它挤掉了 Manufacturing 的 `knowledge_update_10` 原排第十的支持消息，因此保留回复自身的内容分数。

选定规则改变了 11 道多跳题、2 道时间题和 1 道拒答题。规则是在开发集上选定的，15 条标注来自已知失败。后续可固定候选池、十条上下文和两个回复位置，仅比较 BM25 和 E5 对回复候选的排序，先检查第五名这类明确支持能否前移，再决定是否值得新增问答实验。

金融服务器上的 CPU 单进程计时覆盖全部 179 题。索引已经建好，每题执行一次 `rank_content`，中位用时 92.21 ms。同一题复用该分数，预热一次 `expand` 后计时 11 次，取每题中位数。179 个题级中位数的中位值为 0.010 ms，P95 为 0.032 ms。计时使用 Python 3.10.20 的 `perf_counter_ns`，只覆盖检索和扩展阶段。

## 复现

```bash
git submodule update --init external/GroupMemBench
python scripts/probe_reply_retrieval.py
```

脚本会在全部 179 道开发题上逐条核对原 BM25 的消息 ID 和分数，输出上述消融表、15 条标注记录和 14 道变化题的完整最终排序。已有本地权重时，可用下列命令复现问答实验。

```bash
python scripts/run_local_baselines.py --methods bm25-reply --full --partition dev \
  --domains Finance Technology Healthcare Manufacturing \
  --model "$QWEN_MODEL" --model-revision b968826d9c46dd6066d109eabc6255188de91218 \
  --embedding-model "$E5_MODEL" --embedding-revision ffb93f3bd4047442299a41ebb6fa998a38507c52 \
  --output results/runs/bounded-reply-dev
```

运行前将两个环境变量设为 Part 1 使用的本地模型目录，并选择新的输出路径。`bm25-reply` 不构建 E5 索引。若使用多卡独立分片，合并时也显式指定 `--methods bm25-reply --partition dev`。资源与划分约定见[实验协议](experiment-protocol.md)。

复核已完成的实验无需 GPU。金融服务器上的原始结果在本仓库的 `results/runs/bounded-reply-dev-20261117`。可携带的完整记录为 `results/exports/SGMem-Part3-bounded-reply-dev-20261117.tar.gz`，SHA256 为 `864354f9e4468bd1271d2694a004af3d33593c67e4dfb9f5c2c46fb7e44f7d86`。解压本轮与 Part 1 的证据包后，可从两个目录重算本文数字和提示哈希。

```bash
python scripts/analyze_reply_qa.py --run /path/to/bounded-reply-dev-20261117 \
  --bm25-audit /path/to/part1-full-20261105/generation-audit.jsonl
```
